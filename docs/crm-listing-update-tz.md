# ТЗ для CRM: обновление объявлений в Pin через Pin Bridge

## Цель

Когда в CRM меняется объект недвижимости, уже опубликованный в Pin (цена, описание, фото,
характеристики и т.д.), изменение должно автоматически попасть в объявление на pin.tt.

## Как это устроено (важно)

```
CRM  ──PUT /v1/connections/{connection_id}/listings/{external_id}──▶  Pin Bridge  ──PATCH /api/v1.6/items/{id}/──▶  pin.tt
```

- **CRM никогда не обращается к pin.tt напрямую.** Pin пускает запросы только с IP бриджа.
  `PATCH /api/v1.6/items/{id}/` отправляет только бридж.
- **Для CRM отдельного метода «обновить» нет.** Обновление — это тот же запрос, что и публикация:
  `PUT /v1/connections/{connection_id}/listings/{external_id}` с **полным** документом
  объявления. Бридж сам видит, что объявление уже есть в Pin (по `external_id`), и вместо
  создания отправляет в Pin PATCH с полным телом.
- CRM не хранит и не передаёт Pin `item_id`. Объявление определяется парой
  `connection_id` + `external_id` (id объекта в CRM).

## Что нужно сделать в CRM

### 1. Триггер

При сохранении объекта, который уже отправлялся в Pin (есть запись о публикации и
`desired_state` не `removed`), поставьте в очередь задачу «синхронизировать с Pin».
Отправляйте запрос из фоновой задачи, а не из HTTP-запроса пользователя.

Можно отправлять при каждом сохранении: если документ не изменился, бридж ответит `200` и
ничего не сделает в Pin.

### 2. Запрос

```
PUT {PB_URL}/v1/connections/{connection_id}/listings/{external_id}
Content-Type: application/json
Authorization: Bearer <API key>
X-Timestamp: <unix seconds>
X-Nonce: <random 16–128 chars>
X-Signature: v1=<HMAC-SHA256>
Idempotency-Key: <external_id>:<updated_at объекта>
```

- **Подпись** — та же, что уже используется для публикации (docs/agency-api-auth.md):
  canonical string `timestamp\nnonce\nPUT\npath\nsha256(body)`. Подписывайте именно те байты,
  которые отправляете: сериализуйте JSON один раз.
- **Тело — полный документ объявления** в том же формате, что при первой публикации
  (docs/agency-api-listings.md), со всеми полями, а не только изменёнными. Поле, которого
  нет в теле, считается удалённым. `external_id` в теле можно не передавать; если передаёте,
  он должен совпадать с URL.
- **Idempotency-Key** — `<external_id>:<updated_at объекта>` (как сейчас). Новая версия объекта
  получает новый ключ, а повтор того же запроса после сетевой ошибки безопасен. Тот же ключ с
  другим телом вернёт `422 idempotency_key_reused`. Если нужно переотправить неизменённый объект
  после `failed`, используйте новый ключ (например, с суффиксом попытки).

### 3. Фото

- Передавайте полный список URL фото в нужном порядке (максимум 16).
- Неизменённый URL не скачивается повторно.
- **Если фото заменили, у него должен быть новый URL** (например, с хешем или версией в имени
  файла). Новый файл под старым URL бридж не заметит.

### 4. Ответы

| HTTP | Значение | Что делать в CRM |
| --- | --- | --- |
| `202` | Принято, в очереди на отправку в Pin | Статус «обновляется», ждать вебхук |
| `200` | Ничего не изменилось | Ничего |
| `422 invalid_listing` | Данные не прошли проверку, в Pin ничего не ушло | Показать `error.details.errors` пользователю |
| `404` | Неизвестное подключение или объявление | Залогировать; проверить `connection_id` |
| `409 connection_not_active` | Подключение Pin отключено | Попросить переподключить аккаунт |
| `401` | Неверная подпись или время | Проверить ключи и часы сервера (NTP) |
| `429` | Лимит запросов | Повторить через `Retry-After` секунд |
| `5xx` / таймаут | Временная ошибка | Повторить с тем же `Idempotency-Key` |

### 5. Результат — через вебхуки

Ответ `202` означает только «принято». Узнать, что Pin применил изменения, можно из вебхуков
(docs/agency-api-webhooks.md):

- `listing.synced` — Pin обновлён. Сохраните `listing.pin.status`, `listing.live`,
  `listing.warnings`.
- `listing.failed` — не получилось. Причина в `listing.last_error.code`:
  - `pin_rejected` — Pin отклонил данные (`pin_errors`): показать пользователю, после правки
    отправить `PUT` снова;
  - `connection_reauth_required` — нужно переподключить аккаунт Pin; после этого бридж
    дошлёт изменения сам;
  - `image_unavailable`, `pin_unavailable`, `mapping_failed` — отправить `PUT` ещё раз позже.
- `listing.status_changed` — после редактирования Pin может снова отправить объявление на
  модерацию (`on_moderation`), а потом опубликовать или отклонить его. Показывайте актуальный
  `pin.status`.

Правила обработки вебхуков: проверять подпись `X-PinBridge-Signature`, отвечать `2xx` за
10 секунд, дедуплицировать по `id`, игнорировать события с `listing.version` меньше уже
сохранённой.

Если вебхук не пришёл, текущее состояние можно получить через
`GET /v1/connections/{connection_id}/listings/{external_id}`.

### 6. Что CRM делать не должна

- Не вызывать pin.tt и не отправлять `PATCH` куда-либо самой.
- Не отправлять частичные документы (только изменённые поля).
- Не хранить и не использовать Pin `item_id` для запросов (только для отображения).
- Не создавать новое объявление с другим `external_id` ради правки: это будет дубль в Pin.

## Критерии приёмки

1. Меняем цену опубликованного объекта в CRM → в течение минуты приходит `listing.synced`,
   а на pin.tt у объявления новая цена (тот же `item_id`, без дубля).
2. Повторное сохранение без изменений → бридж отвечает `200`, в Pin запросов нет.
3. Заменяем фото (новый URL) → в Pin новое фото, остальные фото не загружаются заново.
4. Отправляем невалидные данные → `422` с ошибками по полям, показанными пользователю;
   объявление в Pin не меняется.
5. Сетевой сбой при отправке → повтор с тем же `Idempotency-Key` не создаёт дублей.
6. Пользователь видит статусы: «обновляется» → «опубликовано» / «на модерации» / ошибка с
   причиной.
