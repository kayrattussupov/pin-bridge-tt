# Публикация на pin.tt напрямую, с готовым токеном

Как со своего компьютера руками проверить публикацию объявлений через API Pin, **минуя Pin Bridge**,
с уже выданной парой `Device-Api-Key` + `Authorization: Token`. Цель — увидеть своими глазами
ответы `validate_ad`, `items`, `pics`, `toggle_active`, `to_remove` и занести их в
[pin-api-verified.md](pin-api-verified.md).

Pin Bridge подключить готовый токен не умеет (он получает токен только через SMS), поэтому здесь
отдельный скрипт [scripts/curl/pin-direct.sh](../scripts/curl/pin-direct.sh).

## Правила для невосстановимого токена

Новый токен получить нельзя, поэтому:

- **Не вызывать** `POST /items/device_api_key/` и `/users/phone_verify/`: скрипт их не умеет
  специально. Новый device key — это новый пустой пользователь Pin, к токену он не подойдёт.
- Ключи лежат только в `scripts/curl/pin-test.env` (в `.gitignore`, права 600). В репозиторий,
  чаты и скриншоты их не копировать. Скрипт их не печатает и не передаёт в командной строке.
- Если запрос вернул `401`/`403` **в JSON** (не HTML Cloudflare) — остановиться и разобраться, а не
  повторять: значит, Pin больше не принимает токен.
- Публиковать только аренду дешевле 4000 TT$ (бесплатно) и сразу убирать.

## 0. Подготовка

Нужны `bash` и `curl` (Git Bash или WSL на Windows), `jq` — по желанию, для красивого вывода.

```bash
cd scripts/curl
source pin-test.env
```

### Доступ к pin.tt: allowlist

API Pin пускает только IP из allowlist (сервер Pin Bridge). С домашнего IP любой запрос получит
`403` со страницей Cloudflare «Just a moment…» — проверено 06.10, скрипт так и пишет:
`(HTML page, not JSON …) HTTP 403`.

Ходим через сервер, SOCKS-туннелем по SSH (ничего на сервере ставить не нужно):

```bash
# в отдельном окне, держать открытым
ssh -N -D 1080 <user>@<сервер Pin Bridge>
```

```bash
export PIN_PROXY=socks5h://127.0.0.1:1080
```

Запросы уходят с IP сервера, а скрипт, файлы и фото остаются на вашем компьютере. Другой вариант —
скопировать `pin-direct.sh`, `pin-test.env` и `examples/pin-item.json` на сервер (`scp`) и запускать там.

| #   | Команда                                   | Ожидается                                                        |
| --- | ----------------------------------------- | ---------------------------------------------------------------- |
| 0.1 | `./pin-direct.sh my` **без** `PIN_PROXY`  | `HTML page … HTTP 403` — подтверждает, что дело в allowlist       |
| 0.2 | `./pin-direct.sh my` с `PIN_PROXY`        | `HTTP 200`, JSON со списком объявлений пользователя (может быть пустым) |

0.2 — главная проверка токена. Если там `401`/`403` в JSON — дальше не идём.

## 1. Справочники (ничего не меняют)

| #   | Команда                          | Что записать                                                         |
| --- | -------------------------------- | -------------------------------------------------------------------- |
| 1.1 | `./pin-direct.sh tree > tree.json`          | дерево рубрик; найти 21 (аренда жилья), 20 (продажа)      |
| 1.2 | `./pin-direct.sh form 21 > form-21.json`    | **поля аренды**: ключи атрибутов, обязательные, id вариантов |
| 1.3 | `./pin-direct.sh cities`                     | id регионов (у нас: 17 Central, 18 NE, 21 NW, 22 SE, 23 SW, 15 Tobago) |
| 1.4 | `./pin-direct.sh districts 17`               | районы Central                                            |

По `form-21.json` заполните `attrs` в [examples/pin-item.json](../scripts/curl/examples/pin-item.json):
ключ — slug поля, значение — **id варианта** (не подпись), для мультивыбора — массив id.
Пример формы: `"attrs": {"type": 123, "bedrooms": 456, "number-of-bathrooms": 789}`.
Это же сверяет наш парсер [rubric-form.ts](../src/dictionaries/rubric-form.ts) с реальным ответом.

## 2. Сухой прогон: `validate_ad` (ничего не создаёт)

| #   | Команда                                                           | Ожидается                                       |
| --- | ----------------------------------------------------------------- | ----------------------------------------------- |
| 2.1 | `./pin-direct.sh validate examples/pin-item.json` с пустым `attrs` | ошибки по обязательным полям — записать формат ошибок |
| 2.2 | то же после заполнения `attrs`                                     | `2xx`, без ошибок                               |
| 2.3 | `title` = `""`                                                     | ошибка по `title`                               |
| 2.4 | `"city": 999`                                                      | ошибка по `city`                                |
| 2.5 | `"price": 9000`                                                    | есть ли признак платного размещения в ответе?    |

Копию для негативных проверок удобно делать так:
`sed 's/"city": 17/"city": 999/' examples/pin-item.json > /tmp/bad.json`.

## 3. Фото

```bash
./pin-direct.sh pic photo.jpg          # JPEG или PNG
```

Ожидается `2xx` и `{"id": …}`. Впишите id в `"images": [<id>]` и повторите 2.2.
Проверить: лимит размера, что будет с `.webp` (ожидаем отказ).

## 4. Публикация (реальное объявление)

| #   | Команда                                                  | Ожидается                                                                 |
| --- | -------------------------------------------------------- | ------------------------------------------------------------------------- |
| 4.1 | `./pin-direct.sh create examples/pin-item.json`          | скрипт проверит, что `direct-test-1` ещё нет, спросит `y`; `2xx`, `id` объявления |
|     | `export ITEM=<id из ответа>`                             |                                                                           |
| 4.2 | `./pin-direct.sh find direct-test-1`                     | объявление есть, `external_id` сохранился, `status` (0 опубл., 1 модерация) |
| 4.3 | Повтор 4.1                                               | скрипт откажет: `already on Pin` (защита от дублей)                       |
| 4.4 | Открыть объявление на pin.tt в браузере                  | заголовок, цена, регион, атрибуты, фото как в JSON                        |
| 4.5 | `./pin-direct.sh my`                                     | `not_paid`, `moderator_comment` — записать поля                           |

Через 5–15 минут повторите 4.2: как и когда меняется `status` после модерации.

## 5. Изменения

| #   | Команда                                                                        | Ожидается                                |

| 5.4 | `./pin-direct.sh update 999999999 /tmp/edit.json`                              | `404` — формат ошибки                    |
| 5.5 | `./pin-direct.sh toggle $ITEM`, затем `find direct-test-1`                     | `status: 2` (скрыто)                     |
| 5.6 | `./pin-direct.sh toggle $ITEM`, затем `find direct-test-1`                     | снова `0`/`1`                            |

## 6. Удаление и уборка

| #   | Команда                               | Ожидается                                                        |
| --- | ------------------------------------- | ---------------------------------------------------------------- |
| 6.1 | `./pin-direct.sh remove $ITEM`        | `2xx`                                                            |
| 6.2 | `./pin-direct.sh find direct-test-1`  | пропало из `front_my` или осталось с другим `status` — записать |
| 6.3 | `./pin-direct.sh remove $ITEM` ещё раз | `404` или `2xx` — записать (важно для повторов в worker)        |
| 6.4 | `./pin-direct.sh my`                  | тестовых объявлений не осталось                                  |

Закрыть SSH-туннель (Ctrl+C). Файл `pin-test.env` не удалять, пока токен нужен для тестов.

## Что занести в pin-api-verified.md

Для каждого шага — статус, дата и фактический ответ (без ключей и телефонов), особенно:

- форма ответа `rubric_form/21` и сработал ли наш парсер;
- формат ошибок `validate_ad` и `POST /items/` (на что опирается `classify.ts`);
- ответ `POST /items/`: где `id`, есть ли `status`, `not_paid`;
- поведение повторного `update`, повторного `to_remove`, `toggle_active`;
- отличаются ли ответы от описания Pin (как с `id`/`uuid` у device key).
