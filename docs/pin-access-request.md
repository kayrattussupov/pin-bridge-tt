# Запрос к Pin: allowlist сервера и тестовый номер

> **06.10: сервер уже в allowlist** (`device_api_key` отвечает 201, см.
> [pin-api-verified.md](pin-api-verified.md)). Пункт 1 отправлять не нужно, остальные актуальны.

Перед отправкой запустите на сервере проверку и приложите её вывод (файл уже без секретов):

```bash
cd /opt/pin-bridge/scripts/curl     # или туда, где распакован архив
./pin-check.sh                      # создаёт pin-check.txt
```

Скрипт обращается к pin.tt обычным curl, Pin Bridge для него ставить не нужно. В файле:
IPv4 и IPv6 сервера, ответ `POST /items/device_api_key/` (статус, `server`, `cf-ray`) и, если
ключ выдан, ответы справочников. Если в конце `RESULT: device key issued`, сервер уже пускают,
и в запросе остаётся только номер.

## Текст (подставьте IP и cf-ray из pin-check.txt)

> Привет! Мы готовы подключаться к API pin.tt с нашего сервера, он будет единственной точкой
> выхода ко всему API (через него пойдут запросы всех агентств).
>
> **1. Allowlist.** Пожалуйста, добавьте в allowlist Cloudflare для `pin.tt/api/*`:
>
> - IPv4: `<IPv4 из pin-check.txt>`
> - IPv6: `<IPv6 из pin-check.txt, если есть>` (все запросы идут по IPv4, но на всякий случай)
>
> Сейчас с этого IP первый же запрос получает 403 от Cloudflare:
>
> ```
> curl -4 -i -X POST https://pin.tt/api/v1.6/items/device_api_key/ \
>   -H 'Content-Type: application/json' -H 'Accept: application/json' -d '{}'
> HTTP 403, server: cloudflare, cf-ray: <cf-ray из pin-check.txt>, <дата из pin-check.txt UTC>
> ```
>
> Полный вывод проверки прикладываю (pin-check.txt). После добавления прогоним её ещё раз и
> пришлём результат.
>
> **2. Тестовый номер.** Нужен тестовый номер +1868 с постоянным кодом для `phone_verify`,
> о котором вы писали, чтобы проверять логин и публикацию без реальных SMS. Наш казахстанский
> номер не подходит: `{"status": 1, "errors": ["Could not determine the country by number"]}`.
>
> **3. Лимиты.** Все запросы агентств идут с одного IP. Есть ли лимиты запросов на IP или на
> весь API (кроме 5 SMS на ключ устройства за 10 минут), о которых нам стоит знать? Мы со своей
> стороны держим не больше 5 запросов в секунду (настраивается).
>
> **4. Пустые пользователи.** Каждый `POST /items/device_api_key/` создаёт у вас нового
> пользователя (в ответе `"user": 1120268`, `1120272`, …). Мы создаём ключ на каждый подключённый
> номер (чтобы лимит SMS считался отдельно) плюс один служебный для справочников. Это нормально
> для вас, или лучше переиспользовать ключи?
>
> **5. Формат `rubric_form`.** Если есть пример ответа `GET /api/v1.6/items/rubric_form/21/`,
> пришлите, пожалуйста: разбираем его по описанию, а формат нигде не описан.
>
> Спасибо!

## После ответа Pin

```bash
./pin-check.sh                                                # RESULT: device key issued
PIN_PHONE=+1868XXXXXXX ./pin-check.sh                         # придёт SMS (или постоянный код)
PIN_PHONE=+1868XXXXXXX PIN_CODE=<код> PIN_DEVICE_KEY=<uuid с экрана> ./pin-check.sh
                                                              # -> token issued
```

Дальше обычный порядок из [deploy-ubuntu.md](deploy-ubuntu.md): `pb-smoke` на сервере, затем
curl-тесты с компьютера (`smoke.sh`, `connect.sh`, `publish.sh`).
